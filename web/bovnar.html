The Problems Bovnar Solves

Other formats serialize the value.
Bovnar serializes the truth.

JSON gives you 9.81. Bovnar gives you <float:64,m/s²> 9.81 — a 64-bit double, in meters per second squared, that any system can read correctly without asking anyone what it means.

P1

Units vanish at every boundary

Is 9.81 acceleration, wind speed, or a ratio? JSON has no answer. Comments help if someone remembered to write one.

P2

Bit-width is completely invisible

A 12-bit ADC reading and a 64-bit timestamp both look like "number." Misread the width and you overflow — silently.

P3

Schema files create permanent coupling

A Protobuf blob without its .proto is unreadable. You've turned your data into a hostage of the toolchain that produced it.

P4

Binary payloads demand Base64 overhead

Embedding a sensor burst in JSON inflates it 33% and forces an encode/decode round-trip on every read and write.

Problem 1 · Unit ambiguity

A number without a unit is a liability.

A value leaving a measurement system in m/s² arrives in the next one as a bare float. JSON, Protobuf, and YAML all silently drop the physical dimension. The unit ends up in a comment, a wiki, or nowhere.

Bovnar validates the full unit — SI/IEC prefixes, compound expressions — at parse time and exposes it as structured value_unit_t data in the C API. It travels with the value. It cannot be lost.

1234567891011
# JSON — the unit is anyone's guess "acceleration": 9.81, "voltage": 3.3, "storage": 8589934592, "temp_range": -40 # Bovnar — unit is part of the type .acceleration = <float:64,m/s²> 9.81; .voltage = <float:32,V> 3.3; .storage = <uint:64,Gi~B> 8; # 8 GiB .temp_range = <sint:8,°C> -40;
Problem 2 · Invisible bit-width

JSON's "number" is a disaster for hardware interfaces.

A 12-bit ADC sample, a 16-bit port, and a 64-bit nanosecond timestamp are all represented identically. Deserialisation code must assume a width. When that assumption is wrong, the failure is silent.

Bovnar accepts any positive integer as a bit-width — including non-power-of-two widths like uint:12 that map directly to ADC and DAC hardware without padding or guessing.

12345678910111213
# Any bit-width — exact hardware match .adc_raw = <uint:12> 3071; # 12-bit ADC .dac_out = <uint:10> 512; # 10-bit DAC .port = <uint:16> 443; .timestamp = <uint:64,µ~s> 1715000000123456; # Non-decimal: must be quoted strings .crc32 = <uint:32,_16> "A1B2C3D4"; .mask = <uint:8,_2> "11010110"; .guid = <uint:128,_16> "deadbeef" "cafebabe" "0123456789abcdef";
Problem 3 · Schema dependency

A file you can't read without another file isn't portable.

Protobuf is meaningless without its .proto. Avro needs a registry. MessagePack needs agreed-upon field indices. Every binary format turns your data into a hostage of the toolchain that produced it.

A .bvnr file is completely self-contained. Hand it to a colleague, a regulator, or a future version of yourself — they have everything needed to interpret every value. No schema, no toolchain, no archaeology.

123456789101112
# .bvnr — fully self-contained .experiment = "thermal_runaway_001"; .recorded_at = <uint:64,s> 1715000000; .threshold = <float:32,°C> 80.0; .alarm = triggered; .channels = [ {.id = <uint:8> 0; .temp = <float:32,°C> 27.3;}, {.id = <uint:8> 1; .temp = <float:32,°C> 112.4;} ];
Problem 4 · Base64 overhead

Binary data doesn't belong in a text encoding.

Embedding a firmware image or sensor burst in JSON means 33% size inflation, a mandatory encode on write, and a mandatory decode on every read. It's a tax on data that was never meant to be text.

Bovnar's octet stream escape embeds raw binary in-line. A NUL byte switches the parser into chunk mode. No encoding, no inflation. Network frames, calibration blobs, and compressed payloads land naturally alongside structured text fields.

12345678910111213
# Text and raw binary in one document .frame = { .type = data_frame; .seq = <uint:32> 42; .ts = <uint:64,µ~s> 1715000000123456; # NUL opens chunk mode; 2nd NUL closes .payload = \x00\x01\x08\x00 \xDE\xAD\xBE\xEF \xCA\xFE\xBA\xBE\x00; .crc32 = <uint:32,_16> "A1B2C3D4"; };
Problem 5 · Missing numeric types

Embedded DSP and finance both deserve better than "float."

Fixed-point is ubiquitous in embedded and DSP code. Exact decimal is essential in finance and metrology. Neither has a standard serialisation type — people store raw integers and rely on out-of-band knowledge of the Q parameter.

Bovnar's float_fix carries the Q parameter inside the annotation. float_dec (IEEE 754-2008) gives exact decimal in 32 to 256 bits. Both are first-class types, not conventions.

12345678910111213
# float_fix — Q~format (wire = raw × 2⁻Q) .pid_gain = <float_fix:32,q16> 1.002; .adc_temp = <float_fix:16,q8,°C> 23.5; .vel_fx = <float_fix:32,q8,m/s> 9.81; # float_dec — exact decimal (IEEE 754-2008) # 0.1 + 0.2 = 0.3 — not a rounding error .price = <float_dec:32> 12.99; .pressure = <float_dec:64,Pa> 101325.0; .pi_128 = <float_dec:128> # 34 digits 3.14159265358979323846264338327950288; .root2_256 = <float_dec:256> # 70 digits 1.4142135623730950488016887242096981;
Problem 6 · Streaming & fault tolerance

One corrupt record shouldn't sink the whole stream.

DOM parsers require the entire document in memory. One malformed byte in a JSON log stream discards everything that follows. Production pipelines can't afford that fragility.

Bovnar's SAX-style reader uses constant memory regardless of document size. Optional continue_on_error resyncs to the next ; after any error — one bad assignment never silences the rest of the file.

1234567891011121314
/* Incremental reader — constant memory */ bvnr_read_flags_t flags = { .on_verified = my_handler, .on_error = my_err_fn, .continue_on_error = true, .max_file_size = 16777216 /* 16 MiB */ }; bvnr_reader_t r; bvnr_open_read_mem( &r, buf, len, NULL, 0, &flags); bvnr_read(&r); uint64_t skipped = bvnr_reader_get_recovery_count(&r);

The properties that fall out of
solving those six problems properly.

Not bolt-ons. Not workarounds. Design decisions baked into the format from the start.

Self-describing values

Type family, bit-width, numeral base, and physical unit travel in the same byte stream as the value. Interpretable in isolation — by anyone, forever.

per-value annotation · no side channel

SI & IEC units, validated

46+ base units, full SI prefix table (quecto→quetta), IEC binary prefixes (kibi→quebi). Compound expressions with exponents. Caught at parse time, not at runtime.

<float:64,k~g·m/s²> · <uint:64,Gi~B>

Six numeric type families

uint · sint at any bit-width. IEEE 754 binary float (16-bit half to 32768-bit extended). Q~format fixed-point. IEEE 754-2008 decimal float. UTF-8 strings.

uint · sint · float · float_fix · float_dec · utf8

Text-binary hybrid

NUL-escape octet streams embed raw binary in-line. No Base64. No inflation. The UTF-8 validator suspends for the duration; the writer API handles the wire protocol.

0x00-delimited · chunk protocol

SAX-style streaming reader

Two-phase callback architecture. on_unverified fires before semantic validation, on_verified after. Constant memory. Parse any file size without loading a DOM.

pull-based · callback-driven · no DOM

Explicit type annotations

The annotation sits between = and the value. Three optional parameters in any order: width, _base, and unit. Without one, Bovnar synthesises a sensible default.

  • Positive integer → uint:64, negative → sint:64, decimal → float:64
  • Any positive integer is a valid bit-width, incl. uint:12
  • Non-decimal values must be quoted strings — bare FF is a symbol, not a number
1234567891011121314151617181920
# Default synthesis .count = 42; # → uint:64 .offset = -7; # → sint:64 .ratio = 3.14; # → float:64 # Explicit annotation .port = <uint:16> 443; .temp = <float:32> 23.5; .ts = <uint:64,µ~s> 1715000000123456; # Non-power-of-two — ADC/DAC hardware .adc12 = <uint:12> 3071; # 12-bit .dac10 = <uint:10> 512; # 10-bit # Non-decimal: quoted strings only .crc = <uint:32,_16> "A1B2C3D4"; .mask = <uint:8,_2> "11010110"; .perm = <uint:16,_8> "755"; .nan = <float:64> $nan$; .inf = $infinity$;

Physical units built in

Units are a first-class annotation parameter, validated at parse time. The C API exposes them as structured value_unit_t data — prefix, base unit, and exponent per component.

  • SI prefix requires a ~ separator: k~m, µ~s, G~Hz
  • IEC binary: Ki~B, Gi~B, Ti~B — same rule
  • Compound: · or * for multiplication, / for division
  • Exponents: m² or m^2; s⁻¹ or s^-1
1234567891011121314151617181920
# Simple units .timeout = <float:64,s> 2.5; .voltage = <float:32,V> 3.3; .distance = <uint:64,m> 384400000; # SI prefixes — mandatory tilde .frequency = <float:64,G~Hz> 2.4; .resistance = <float:32,k-Ω> 4.7; .delay = <float:32,µ~s> 50.0; # IEC binary prefixes .ram = <uint:64,Gi~B> 8; .disk = <uint:64,Ti~B> 2; # Compound units .velocity = <float:64,m/s> 9.81; .acceleration = <float:64,m/s²> 9.81; .force = <float:64,k~g·m/s²> 9.81; .energy = <float:64,k~g·m²/s²>1000; # Inline suffix (scalar context only) .speed = 9.81 m/s;

Arrays & Structs

Arrays use bracket syntax; / separates rows for multi-dimensional data. Annotations may be per-element or applied to the whole array. Structs nest up to 255 levels with { }.

  • Consecutive commas produce null elements: [,1,,2,]
  • Arrays of structs are the idiomatic record-list pattern
  • References: &.path.to.key — stored as paths, application-resolved
  • Symbols (bare words) for enum-like values: running, true
1234567891011121314151617181920
# Whole-array annotation .temps = <float:32,°C> [23.5,24.1,22.8]; # 2-D matrix — rows separated by / .R = <float:64> [1.0, 0.0, 0.0 ] /[0.0, 0.866,-0.5 ] /[0.0, 0.5, 0.866]; # Struct nesting .config = { .host = "db.internal"; .port = <uint:16> 5432; .tls = true; }; # Array of structs — record list .users = [ {.id=<uint:32> 1; .name="Alice"; .role=admin;}, {.id=<uint:32> 2; .name="Bob"; .role=user;} ];

Fixed-point & Decimal floats

float_fix (Q~format): wire value is a signed integer; mathematical value is raw × 2⁻Q. The Q parameter lives in the annotation — no out-of-band knowledge required.

float_dec (IEEE 754-2008): exact decimal storage in 32 to 256 bits. Binary floats cannot represent 0.1 exactly. Decimal floats can. Essential for financial and metrological data.

1234567891011121314
# float_fix — Q~format (wire = raw_int × 2⁻Q) .adc = <float_fix:16,q8> 3.14; .pid = <float_fix:32,q16> -1.5; .vel_fx = <float_fix:32,q8,m/s> 9.81; .cnt_fx = <float_fix:64,q0> 4096; # Q0=int # float_dec — exact decimal (IEEE 754-2008) # 0.1 + 0.2 = 0.3 (not 0.30000000000000004) .price = <float_dec:32> 12.99; .press = <float_dec:64,Pa> 101325.0; .pi_128 = <float_dec:128> # 34 digits 3.14159265358979323846264338327950288; .root2 = <float_dec:256> # 70 digits 1.4142135623730950488016887242096981;

Inline binary mode

A NUL byte (0x00) in value position switches the parser into binary chunk mode. The UTF-8 validator suspends. No Base64, no encoding overhead.

Wire: 0x00 open → 0x01 LL LL data… chunk (little-endian uint16; 0x0000 = 65536 B) → 0x00 close. The writer API generates this format; you never write wire bytes by hand.

123456789101112131415
# Text + raw binary — one document .frame = { .type = data_frame; .sequence = <uint:32> 42; .ts = <uint:64,µ~s> 1715000000123456; # NUL opens; 2nd NUL closes chunk stream .payload = \x00\x01\x08\x00 \xDE\xAD\xBE\xEF \xCA\xFE\xBA\xBE\x00; .crc32 = <uint:32,_16> "A1B2C3D4"; }; # → ev_octet_stream_start/ev_data(8B)/end
